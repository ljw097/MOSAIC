# 위협 모델과 보안 분석

## 공격자 유형별 분석

| 공격자 | 볼 수 있는 것 | 볼 수 없는 것 (설계 목표) |
|---|---|---|
| **사용자의 ISP·로컬 네트워크 운영자** | 사용자가 MOSAIC 게이트웨이에 연결한다는 사실, 대략적인 대역폭 상한 | 목적지, 내용, 실제 통신하는 시점 (상향 Poisson 커버, 하향 더미가 있고 프레임 길이가 모두 같음) |
| **악성 게이트웨이** | 클라이언트 IP, 자기 링크로 오가는 패킷 수 (게이트웨이를 여러 곳 쓰므로 전체 트래픽의 일부) | 목적지와 내용. 루프·드롭 커버와 실제 패킷을 구별하지 못한다 |
| **악성 믹스 노드** | 이전 홉과 다음 홉, 메시지당 조각 최대 1개 (마름모) | 경로상의 위치, 경로 길이, 송신자, 수신자, 내용. 조각을 버리거나 붙잡아 두어도 n-k개까지는 메시지가 도착한다 |
| **여러 노드를 장악한 공격자** | 장악한 노드를 지나는 조각들 | 한 메시지의 조각 k개를 모으려면 서로 다른 경로의 노드를 k개 이상 장악해야 한다. 그렇게 해도 조각마다 Sphinx 계층 암호가 남아 있다 |
| **악성 출구** | 목적지와 (TLS가 아니면) 내용 | 송신자 IP, 게이트웨이, 같은 사용자의 다른 사이트 세션 (사이트마다 출구를 따로 씀) |
| **목적지 웹사이트** | 출구 IP, 통일된 HTTP 헤더 | 사용자 IP, JS 지문, 다른 사이트의 쿠키 |
| **전역 수동 관찰자 (국가급)** | 모든 링크의 타이밍과 양 | 단일 메시지 수준에서 송신자와 수신자를 연결하는 것. 홉마다 지수분포 지연을 주는 Poisson 믹싱과 커버 트래픽이 입출력 상관을 확률적으로 흐린다 |
| **능동 공격자 (패킷 지연·차단·주입)** | 일부 | 재전송은 tag 캐시가, 헤더·페이로드 변조는 MAC과 LIONESS가 감지한다. (n-1) 공격이나 선택적 차단은 루프 손실 경보로 탐지를 시도한다 |
| **"지금 수집, 나중에 해독"하는 양자 공격자** | 녹화한 링크 트래픽 | 링크 계층 내용. ML-KEM-768과 X25519 하이브리드를 쓰므로 둘 다 깨야 한다 |

## 출구 노드를 장악하면: Tor와 무엇이 다른가

일반 인터넷 서버는 MOSAIC을 모른다. 그래서 누군가는 마지막에 그 서버와 직접 TCP 연결을 맺어야 한다.
이 연결점은 Tor, Nym, I2P 아웃프록시 등 어떤 익명 통신 시스템에도 있고, 프로토콜로는 없앨 수 없다.
MOSAIC은 이 문제를 세 겹으로 다룬다.

| | Tor | MOSAIC (일반 인터넷) | MOSAIC (`.mosaic` 서비스) |
|---|---|---|---|
| 출구 장악 시 보이는 것 | 목적지, (TLS가 아니면) 내용, **패킷 타이밍** | 목적지, TLS 암호문의 양 | **출구 자체가 없다** |
| 출구 장악 + 입구(가드/게이트웨이) 관찰 | 타이밍 상관으로 **송신자 특정 가능** (알려진 실전 공격) | 홉마다 Poisson 지연, 커버 트래픽, 조각 분할로 입출력 타이밍이 끊긴다. 통계적으로만, 장기간에 걸쳐 공격할 수 있다 | 해당 없음 |
| 평문 노출 | HTTP면 그대로 노출 | **HTTPS 전용**이 기본. HTTP는 매번 확인을 받고, 다운그레이드 리다이렉트와 HTTP 하위 리소스는 차단 | 종단 간 X25519+ML-KEM. 중간 노드는 조각을 다 모아도 암호문만 얻는다 (테스트로 검증) |
| 사이트 간 연결 | 회로 단위 | 사이트마다 출구가 다르다. 출구 하나는 사용자의 다른 사이트 방문을 보지 못한다 | 해당 없음 |

결국 출구를 장악한 공격자가 얻는 것은 "누군가(익명)가 example.com에 TLS로 접속했다"는 사실이다.
Tor에서 치명적인 출구+입구 타이밍 상관은 믹싱이 막는다. 출구를 신뢰하고 싶지 않은 통신은 `.mosaic`으로 하면 된다.

## 정직하게 밝히는 한계

1. **프로토타입이다.** 코드는 Python으로 작성됐고 감사를 받지 않았다. 부채널 공격 저항성, 상수 시간 동작,
   DoS 저항성은 운영 수준에 못 미친다.
2. **Sphinx 계층은 아직 포스트-양자가 아니다.** 링크 계층만 하이브리드 PQ다. 양자 공격자가 녹화한 트래픽에서
   링크 암호화를 벗겨내지 못하는 한 Sphinx 헤더는 노출되지 않는다. 하지만 악성 노드가 기록한 패킷의
   Sphinx 헤더 자체는 장기적으로 위험하다. Outfox 같은 KEM 기반 패킷 포맷이 로드맵에 있다.
3. **장기 교집합(intersection)·통계적 노출 공격.** 같은 상대와 몇 주, 몇 달씩 반복해서 통신하면, 어떤 믹스넷도
   전역 관찰자의 통계 공격을 완전히 막을 수는 없다. 커버 트래픽 비율을 높이고(`paranoid`) 오래 온라인 상태를
   유지하면 공격이 느려질 뿐이다.
4. **interactive 프로파일은 타협이다.** 홉당 평균 지연 20ms는 Tor보다는 강하다. 하지만 `paranoid`보다 상관
   공격에 훨씬 취약하다.
5. **신뢰성.** 링크가 TCP라서 정상 상황에서는 패킷이 사라지지 않는다. 노드 하나가 다운되거나 패킷을 버려도
   메시지마다 n-k개까지는 마름모 분할이 흡수한다. 그보다 큰 손실이 나면 스트림이 멈추고 타임아웃(120초)으로 끝난다.
6. **Sybil 공격.** 권한 서버가 등록을 제한하지 않는다. 운영망에는 운영자 검증, 대역폭 측정, 패밀리 선언이 필요하다.
7. **키 로테이션.** Sphinx 키는 노드가 실행되는 동안 고정이다. 운영 버전에서는 epoch마다 키를 바꿔야
   전방향 안전성이 생기고 재전송 캐시도 한정된다.
8. **브라우저 호환성.** 정화 모드는 JS가 필요한 사이트(SPA, 일부 로그인)를 깨뜨린다. `--chromium --allow-js`
   호환 모드는 동작은 하지만 Chromium 지문을 드러낸다.
9. **사용자 행동.** 로그인, 실명 입력, 같은 계정을 쓰는 것은 어떤 프로토콜로도 숨길 수 없다.

10. **마름모의 두 꼭짓점.** 일반 인터넷 접속에서는 출구가 메시지를 복원해야 하므로 모든 조각을 받는다
    (오른쪽 꼭짓점). 그래서 출구 단에서는 분할이 기밀성을 더해 주지 않는다. 그 몫은 HTTPS 전용 정책과 종단 간 TLS가
    맡는다. 출구가 아예 없는 경로가 필요하면 `.mosaic` 서비스를 쓴다. 그 경우 오른쪽 꼭짓점은 목적지 자신이다. 왼쪽 꼭짓점인 클라이언트 쪽에서는
    게이트웨이를 여러 곳 쓰는 만큼 IP를 아는 노드도 늘어난다. 기본값 2는 그 사이의 타협이다.
11. **분할 비용.** 대역폭이 약 n/k배 든다. 계층의 믹스 수가 n보다 적으면 같은 노드가 조각 여러 개를 보게 된다
    (고르게 나누긴 한다).

12. **`.mosaic` 서비스의 한계.** 서비스 키는 장기 키라서, 서비스 키가 유출되면 과거 INIT을 녹화해 둔 공격자가
    세션 키를 복원할 수 있다 (서비스 측 전방향 안전성 없음). 서비스의 intro 게이트웨이는 서비스 IP와 받는 조각의
    양을 안다. 서비스 기술자는 합의 문서에 공개되므로 서비스 목록 자체는 숨겨지지 않는다 (블라인드 키 디렉터리는
    로드맵).
